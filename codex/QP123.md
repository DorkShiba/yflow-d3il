# 5번 ON + 1·2·3의 8개 조합 (4번 OFF)

**현재 4-GPU·96 GPU시간 한도에서는 아래의 `20시간 제한과 재개` 명령을 사용한다.**
기존 run_qp123 명령에는 시간 제한이 없다.

기존 4+5 실험을 이번 담당 실험에서 제외한다. 과거 결과와 RTC 코드는 보존한다.

| 비트(1,2,3) | 적용 방법 |
|---|---|
| 000 | 5 |
| 001 | 3+5 |
| 010 | 2+5 |
| 011 | 2+3+5 |
| 100 | 1+5 |
| 101 | 1+3+5 |
| 110 | 1+2+5 |
| 111 | 1+2+3+5 |

1은 projection, 2는 PF2MP, 3은 terminal-plan VLSA, 4는 RTC,
5는 LiPo의 jerk 최소화 QP만 사용한다. 블렌딩은 사용하지 않는다.
1·2·3 코드는 origin/feature/method123_merge의
`5acb1034d0819453fcf6364477cb25f1c30e6d8b`에서 가져왔다.
설정/제약값은 해당 브랜치의 configs/pushing.yaml, inserting.yaml을 유지한다.
Windows 경로/캐시 잠금 호환성, codex 출력 허용 및 아래 평가 경로를 추가했다.

## 실행 순서와 해석

각 ODE 단계: FM + PF2MP → Euler → projection.
최종 계획: VLSA → QP5 → 앞 8개 행동 실행.
ODE 10단계, horizon 16, 제어 주기 0.035초, QP 위치 수정 한도 축별 0.0003m.
RTC 및 추론 지연 모사는 사용하지 않는다. VLSA 실행 시 재투영도 끈다.

QP5는 기존 구현과 같은 목적함수/수정 한도를 사용한다. 앞 단계의 안전 제약을
QP5에 새로 넣거나, QP5 뒤에 추가 투영을 하지 않는다. 따라서 최종 계획의
안전 제약 만족을 보장하지 않는다. rollouts.json의 plan_report.qp5에
before_violation/after_violation을 남기고, 실제 실행 시에도 제약 위반을 측정한다.
계획/솔버 실패는 해당 에피소드의 실패로 집계하며 숨겨서 제외하지 않는다.
행동이 전혀 실행되지 않은 에피소드에는 jerk 지표가 없으므로 smoothness의 n을 함께 확인한다.

각 seed/context/trajectory에 독립적인 난수 생성기를 사용한다. 같은 조합 간 같은
에피소드의 k번째 재계획은 같은 초기 노이즈를 사용하며, 앞 에피소드가 일찍 끝나도
뒤 에피소드의 난수가 밀리지 않는다. PF2MP 캐시는 훈련 데이터만 사용하고
codex/pf2mp_cache에 저장한다. 모델 재학습은 하지 않는다.

## VESSL 실행

먼저 이 변경 파일들이 VESSL 저장소에 반영되어 있어야 한다. 로컬 편집만으로
원격 저장소가 갱신되지는 않는다. 기존 작업이 실행 중이면 그 터미널에서 Ctrl+C로
중단하고, 새 작업은 tmux 안에서 실행한다.

```bash
cd /root/d3il-work/yflow-d3il-rtc
source /root/d3il-work/codex/venv/bin/activate
python -m pip install -r requirements-qp123.txt

# 8개 조합 연결 확인: 조합별 6개 에피소드, 총 48개
python -m fm_constraint.run_qp123 --task pushing --device cuda:0 \
  --hardflow-root /root/d3il-work/codex/HardFlow \
  --d3il-root /root/d3il-work/d3il \
  --n-contexts 3 --n-traj 2 --seeds 0

# 본 실험: 이용 가능한 전체 평가 컨텍스트, 각 4회, seed 3개
python -m fm_constraint.run_qp123 --task pushing --device cuda:0 \
  --hardflow-root /root/d3il-work/codex/HardFlow \
  --d3il-root /root/d3il-work/d3il \
  --n-contexts 0 --n-traj 4 --seeds 0 1 2
```

Inserting은 동일 명령에서 `--task inserting`으로 변경한다. 전체 훈련 NPZ와
manifest, 평가 데이터 및 inserting 컨텍스트가 있어야 한다.
`--dry-run`은 실행할 8개 조합×seed의 명령만 출력한다.
데이터는 기본적으로 현재 저장소 data를 사용하며 `--data-root`로 변경할 수 있다.

결과는 codex/qp123_runs/<시각>/seed_<seed>/m123_<비트>_m4off_m5on/에 저장된다.
experiment.json에는 고정 조건, summary.json에는 완료한 조합별 성공률/jerk/시간이
누적된다. 개별 결과에는 에피소드별 결과, 제약 위반, 실패 원인, QP 진단이 남는다.
기준군은 000(5번만 적용)이다. 기존 RTC 실험 결과와는 난수 방식/평가 구현이 달라
짝지은 비교로 섞지 않는다. 서로 다른 조합의 성공률과 jerk를 함께 비교한다.

이 스크립트는 VESSL 실행/종료를 원격으로 제어하지 않는다. 로컬 CPU 검증과
실제 GPU 환경에서의 closed-loop 성능 검증을 구분한다.

## 로컬 검증 (2026-11-06)

- 통합 테스트 96개 통과, Windows 심볼릭 링크 권한 테스트 1개 건너뜀.
- 추가한 QP 실패 차단 테스트를 포함한 새 조합 테스트 10개 모두 통과.
- 실제 Pushing/Inserting 체크포인트, 실제 훈련 데이터 기반 PF2MP 캐시를 사용해
  태스크별 8개 조합의 단일 계획 생성과 QP5 처리를 CPU에서 확인.
- Pushing 훈련 전이 417,518개, Inserting 훈련 전이 711,908개로 캐시 생성.
- 작은 규모 명령 dry-run에서 8개 서로 다른 조합을 확인.
- VESSL GPU closed-loop 평가는 아직 실행하지 않음. 로컬 결과로 성공률을 주장하지 않음.

## 새 4-GPU 워크스페이스

기존과 같은 실행 이미지/데이터 볼륨을 사용하는 것이 편하다. 새 워크스페이스에는
다음 경로의 실제 파일들이 필요하다. 경로가 달라지면 명령의 옵션을 변경한다.
가상환경 폴더를 그대로 복사하기보다는 기존 실행 이미지나 동일한 Python 환경을 사용한다.

- yflow-d3il-rtc: 최신 코드, fm_baseline/results/{task}_baseline의 checkpoint/config/normalizer
- 저장소의 data/{task}_sincos_v1: 전체 train/val NPZ와 manifest (PF2MP는 train도 필요)
- HardFlow: 기존과 동일한 a85105080dd0a28dca76b49ac0414f275de146ed 버전
- D3IL: 기존 버전과 시뮬레이터 asset, pushing test_contexts.pkl
- Inserting: fm_baseline/contexts/inserting_val.pkl 및 val 데이터. 컨텍스트 파일이 없으면 raw 데이터도 필요
- 선택 사항: 기존 codex/pf2mp_cache를 옮기면 같은 데이터/설정에서 캐시를 재사용

새 이미지에 의존성이 없으면 Python 3.10 환경에 requirements.txt와
requirements-qp123.txt를 설치한다. 이미 검증된 환경이라면 추가 의존성만 설치한다.
기존 환경에서 필요했던 libGL 등 시스템 라이브러리도 갖춰야 한다.

```bash
cd /root/d3il-work/yflow-d3il-rtc
source /root/d3il-work/codex/venv/bin/activate
python -m pip install -r requirements-qp123.txt
nvidia-smi
python -c "import torch; print(torch.cuda.is_available(), torch.cuda.device_count())"

tmux new -s qp123
# 새 tmux 셸에서 환경을 다시 활성화한다.
source /root/d3il-work/codex/venv/bin/activate
cd /root/d3il-work/yflow-d3il-rtc
python -m fm_constraint.run_qp123 --task pushing \
  --devices cuda:0 cuda:1 cuda:2 cuda:3 \
  --cpu-threads 2 \
  --hardflow-root /root/d3il-work/codex/HardFlow \
  --d3il-root /root/d3il-work/d3il \
  --n-contexts 0 --n-traj 4 --seeds 0 1 2
```

새 환경에서는 먼저 위 명령의 마지막 줄을 `--n-contexts 3 --n-traj 2 --seeds 0`으로
바꿔 4-GPU 연결을 확인한다. `--dry-run`은 GPU 없이 배정만 확인할 수 있다.
GPU 번호는 현재 프로세스에 보이는 논리 번호(CUDA_VISIBLE_DEVICES 적용 후)다.

GPU 0에는 000/111, GPU 1에는 001/110, GPU 2에는 010/101, GPU 3에는 011/100을 배정한다.
각 GPU에 PF2MP ON/OFF 조합을 하나씩 분산한다. GPU별로 조합과 seed를
순차 실행하므로 GPU 하나에 평가 프로세스 하나만 실행된다. PF2MP 캐시는 부모가
CPU에서 먼저 준비한다. CPU 수치연산 스레드는 프로세스당 2개로 제한하며,
시뮬레이션·OSQP도 CPU를 사용하므로 CPU/RAM 여유가 필요하다. 4배 가속을 보장하지 않는다.
조합별 작업량이 달라 마지막으로 끝나는 GPU가 전체 시간을 결정한다.

결과 루트의 gpu_assignments.json에 배정, logs/seed_<seed>_m123_<bits>.log에
각 작업의 출력, failures.json에 실패를 기록한다. summary.json은 GPU별 담당
작업이 끝날 때 갱신된다. 한 GPU의 작업 실패 시 그 GPU의 남은 작업을 중단하고
다른 GPU들은 완료시킨 뒤 실행기를 실패 상태로 종료한다. Ctrl+C는 실행기가
시작한 자식 평가 프로세스들을 종료한다. 출력 경로 재사용/자동 재개는 지원하지 않는다.

GPU를 병렬로 쓰는 실행기의 배정·출력 분리·실패 처리는 모의 프로세스 테스트로
검증했다. 실제 4-GPU 워크스페이스에서의 동작은 별도 확인이 필요하다.

## 20시간 제한과 재개

4개 GPU 동시 사용 시 20시간은 80 GPU시간이다. 96 GPU시간 한도에서 나머지
16 GPU시간(4개 기준 4시간)은 준비·종료 여유로 남긴다. 시간 제한은 아래 명령을
시작한 시점부터 계산하며, 프로그램 내부 캐시 준비 시간도 포함한다.
명령 실행 전 설치·복사·대기 시간은 프로그램이 알 수 없으므로 이미 오래 사용한
워크스페이스에서는 --max-hours를 더 줄여야 한다. 최대 허용값은 20이다.

새 실행기는 seed/조합/컨텍스트 단위로 작업을 나눈다. 기본값에서는 한 작업이
컨텍스트 1개 × 궤적 4회다. 완료된 결과·rollout을 확인한 뒤 complete.json을
원자적으로 저장한다. 부모 프로세스가 종료되더라도 이 표시가 남는다.
20시간이 되면 진행 중인 자식 프로세스를 종료하고 추가 작업을 시작하지 않는다.
프로세스 종료 확인에 수 초가 더 걸릴 수 있다.

```bash
# tmux 안에서, 동일한 가상환경을 활성화한 상태
python -m fm_constraint.run_qp123_budget \
  --task pushing \
  --devices cuda:0 cuda:1 cuda:2 cuda:3 \
  --max-hours 20 --cpu-threads 2 \
  --hardflow-root /root/d3il-work/codex/HardFlow \
  --d3il-root /root/d3il-work/d3il \
  --n-contexts 0 --n-traj 4 --seeds 0 1 2 \
  --output-root codex/qp123_budget_pushing
```

재시작 후 동일 명령 끝에 `--resume`만 추가한다. output-root는 반드시 같아야 한다.
새 실행에서도 20시간 한도가 새로 적용된다. 프로그램은 VESSL 할당량을 갱신하지 않는다.
새 워크스페이스로 옮기는 경우 저장소의 codex/qp123_budget_pushing 디렉터리 전체를
영속 볼륨에 보존하거나 복사한다. 이 결과 폴더는 Git 업로드 대상이 아니다.
모델/데이터/코드와 평가 설정도 그대로 유지한다. 경로가 바뀌는 것은 허용되지만
내용이 달라지면 재개를 거부한다. 기존 HardFlow/D3IL 버전·asset도 동일하게 유지한다.

완료 작업은 건너뛰고, 중단된 작업만 새 attempt 디렉터리에서 다시 시작한다.
이전 미완료 시도는 삭제하지 않으며 집계하지 않는다. 재실행 손실은 GPU당 진행 중이던
컨텍스트 1개 분량이다. 분할 전후 전역 컨텍스트 번호와 에피소드 난수를 유지한다.
각 작업이 모델/시뮬레이터를 다시 초기화하므로 장시간 단일 프로세스보다 부가 비용이 있다.

progress.json에서 완료/전체/남은 작업 수와 상태를 확인한다.
`complete`는 전체 완료, `stopped`는 시간 제한 또는 중단 후 재개 필요,
`failed`는 로그를 확인할 오류다. 캐시 준비가 제한에 걸리면
`stopped_during_cache_preparation`으로 기록한다.
summary.json은 완료한 컨텍스트 단위 결과이며, 미완료 결과를 전체 실험 결과로
보고하지 않는다. 전체 성공률은 완료 결과의 에피소드 수로 가중 집계한다.
개별 시도의 results.json에는 전체 에피소드·smoothness·타이밍 자료가 남는다.

중요: 평가 프로그램 종료는 VESSL 워크스페이스 정지가 아니다. 시간 차감을 멈추려면
VESSL에서 워크스페이스도 정지한다. 재시작으로 할당량이 갱신되는지는 해당 워크스페이스
정책을 따른다. 이 실행기는 VESSL 정지/재시작이나 할당량 관리를 자동 수행하지 않는다.

검증: 시간 제한 시 실제 자식 프로세스 종료, 완료 결과 건너뛰기, 손상 결과 차단,
실패 결과 미완료 처리, 컨텍스트 분할 전후 동일 난수를 포함해 관련 테스트 45개 통과,
Windows 심볼릭 링크 권한 테스트 1개 건너뜀. 실제 GPU 시뮬레이션은 VESSL에서 확인한다.
